# 04-pjt · 책사이

책과 사람을 연결하는 Django 도서 커뮤니티입니다. 도서 관리와 회원 인증을 기반으로 사용자별 좋아요, 카테고리 탐색, 관심 카테고리, 좋아요 기반 GPT 도서 추천을 구현했습니다. PDF의 필수 요구사항 **F401~F416, NF401~NF402**와 선택 과제 **F418~F419**를 포함합니다.

기존 `live_code/`는 수업용 할 일 앱이므로 그대로 보존했습니다. **제출용 도서 프로젝트의 실행 위치는 이 README와 `manage.py`가 있는 `pjt_04/`입니다.**

## 실행 방법

Python 3.11 이상과 Django 5.2를 사용합니다. 명세서의 권장 Python 버전은 3.11이며, **Python 3.11.9와 3.12에서 모두 테스트를 통과**했습니다.

```powershell
# pjt_04 폴더에서 실행
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_books
.\.venv\Scripts\python.exe manage.py runserver
```

가상환경과 DB가 준비되어 있다면 서버 실행 명령으로 시작할 수 있습니다. 접속 주소는 **http://127.0.0.1:8000/** 입니다.

- `seed_books`는 선택 사항이며, 같은 제목·저자의 기존 도서는 변경하지 않습니다.
- 예시 평점은 기능 확인용 데이터이며 실제 서비스에서 수집한 평점이 아닙니다.
- 로그인 계정은 회원가입 화면에서 직접 생성합니다. 기본 관리자 계정은 없습니다.
- 관리자 계정이 필요하면 `python manage.py createsuperuser`를 실행합니다.
- Bootstrap 5.3.8 CSS·JS는 `static/vendor/`에 포함되어 실행 중 CDN 연결이 필요 없습니다.
- `.venv/`, SQLite DB, 임시 파일은 `.gitignore`로 제외했습니다.
- AI 도서 추천을 사용하려면 `.env`에 `GMS_KEY`를 설정합니다. 새 환경에서는 `.env.example`을 참고해 작성합니다. `.env`는 자동으로 로드되며 이미 등록된 OS 환경변수가 우선합니다. 값을 변경한 뒤에는 서버를 재시작합니다.

### 도서 관리와 회원 인증

- 로그인 없이 도서 목록과 상세를 확인할 수 있으며, 상세 페이지에서는 제목·저자·카테고리·설명·평점을 표시합니다. 카테고리 이름을 누르면 해당 도서 목록으로 이동합니다.
- 로그인한 사용자는 도서를 등록·수정·삭제할 수 있습니다. 평점은 0.0~10.0 범위로 검증하고, 잘못된 입력은 오류와 함께 다시 표시합니다.
- 회원가입 완료 시 자동 로그인하며, 인증이 필요한 화면에 먼저 접근했다면 로그인 후 안전한 내부 주소로 복귀합니다.
- 마이페이지에서 회원정보와 독서 정보를 확인하고 수정할 수 있습니다. 비밀번호 변경 시 기존 비밀번호를 검증하고 로그인 세션을 갱신합니다.
- 로그아웃·회원탈퇴·도서 삭제·좋아요 변경·관심 카테고리 저장·AI 추천은 POST 요청으로 처리하며, 변경 요청에는 CSRF 검증을 적용합니다.

### 좋아요 기반 GPT 도서 추천

- **내가 좋아요한 책** 페이지 상단의 **추천받기**를 누르면 추천 도서 카드가 표시됩니다. 검색어·카테고리로 목록을 좁혔더라도 추천은 본인의 전체 좋아요 도서를 기준으로 합니다.
- 서버가 제목·저자·카테고리·설명으로 딕셔너리를 구성해 JSON으로 전송합니다. 설명은 도서당 400자로 제한하며 아이디·이메일 등 회원 정보는 포함하지 않습니다.
- 첨부 GMS 가이드의 `https://gms.ssafy.io/gmsapi/api.openai.com/v1/responses` 주소와 Bearer 인증을 사용하며, 모델은 `gpt-5-nano`입니다. API 키는 서버에서만 읽습니다.
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)의 JSON Schema 형식으로 최대 3권의 제목·저자·카테고리·소개·추천 이유를 요청합니다. 서버에서도 필수 필드·자료형·길이를 검증하고 기존 좋아요와 중복 추천을 제외합니다.
- 추천 결과는 화면에 표시합니다. 기존 DB의 도서와 제목·저자가 일치하면 상세 링크를 제공하며, 외부 도서를 공동 책장에 자동 저장하지 않습니다.
- 결과에는 **“추천 도서 정보와 추천 이유는 AI가 생성한 답변으로, 실제 도서 정보와 다르거나 정확하지 않을 수 있습니다.”**라는 문구를 표시합니다.
- 추천 버튼은 **즉시 실행하는 30초 쓰로틀**을 적용합니다. 제한 시간 안의 클릭은 새 요청을 예약하지 않으며, 요청이 끝나지 않았다면 30초가 지나도 중복 실행하지 않습니다. 서버에서도 사용자별 재요청과 진행 중인 요청을 제한하고 429 및 `Retry-After`로 안내합니다.
- 현재 개발 서버의 기본 메모리 캐시로 쓰로틀을 처리합니다. 여러 프로세스로 배포할 때에는 모든 프로세스가 공유하는 캐시를 설정해야 합니다.
- 서버 외부 호출은 60초, 화면 대기는 75초로 제한합니다. 빈 좋아요, 로그인 만료, 키 누락·인증 실패, 요청 한도, 연결·시간 초과, 거절·불완전·잘못된 응답을 처리합니다. 자동 API 재시도는 하지 않습니다.
- GMS에 `store=false`를 전달합니다. 이 설정만으로 중계 서비스의 로그·보관 정책까지 제어되는 것은 아닙니다.

### 사용자별 좋아요

- 도서 목록·상세의 하트 버튼으로 로그인한 사용자의 좋아요를 추가하거나 취소합니다.
- 우측 상단 **♥ 내가 좋아요한 책** 메뉴에서 본인이 좋아요한 도서만 조회합니다. 이 목록에서도 제목·저자 검색을 할 수 있습니다.
- 개인별 상태는 `Book.liked_users` 다대다 관계와 `books_book_liked_users` 중간 테이블에 저장합니다. 최초에는 관계가 없어 모든 사용자에게 좋아요하지 않은 상태입니다. 사용자 전체가 공유하는 불리언 컬럼은 사용하지 않습니다.
- 버튼은 화면 상태를 즉시 갱신하고 **마지막 클릭에서 300ms 후** 최종 상태를 저장합니다. 원래 상태로 돌아온 연속 클릭은 요청을 보내지 않습니다.
- 진행 중인 요청은 순서대로 처리하며, 최종 상태를 명시적으로 전송해 재시도로 좋아요가 뒤집히지 않도록 합니다. 실패 시 화면 상태를 복구하고 오류를 안내합니다.
- 좋아요 목록에서 취소가 저장되면 해당 카드를 제거하고 건수와 빈 목록 안내를 갱신합니다.
- 기존 DB에서는 `python manage.py migrate`를 실행해 새 관계 테이블을 적용합니다.

### 카테고리와 관심 카테고리

- `books_category`에 카테고리 이름을 저장하고, `books_book.category_id`로 각 도서를 연결합니다. 도서가 연결된 카테고리는 삭제되지 않도록 보호합니다.
- 오른쪽 메뉴에 카테고리와 전체 도서 기준의 건수를 표시합니다. 모바일에서는 상단의 가로 메뉴로 표시합니다.
- 카테고리를 선택하면 `/books/categories/<카테고리 ID>/`에서 해당 도서만 조회합니다. 검색어와 내 좋아요 필터도 함께 적용할 수 있습니다.
- 도서 등록·수정 시 기존 카테고리를 선택하거나 새 이름을 입력합니다. **새 이름을 입력하면 기존 선택보다 우선**하며, 다른 입력이 유효할 때 도서와 함께 저장합니다.
- 이름 앞뒤 공백과 연속 공백을 정리하고, 영문 대소문자가 다른 같은 이름은 기존 카테고리를 재사용합니다. 카테고리 선택과 새 이름 모두 없으면 저장하지 않습니다.
- 마이페이지의 **관심 카테고리**에서 여러 항목을 선택·저장·해제할 수 있습니다. 저장은 로그인한 본인에게만 적용하며, 다른 회원정보와 기존 관심 장르는 변경하지 않습니다.
- 선택한 관심 카테고리 링크를 누르면 해당 카테고리의 책을 볼 수 있습니다. 회원가입·회원정보 수정에서도 관심 카테고리를 선택할 수 있습니다.

기존 도서의 제목·저자·설명을 확인해 아래처럼 분류했으며, 데이터 마이그레이션으로 적용합니다. 그 외 분류를 판단할 수 없는 기존 도서는 `기타`로 저장합니다. 새 도서는 사용자가 선택한 카테고리를 사용합니다.

| 카테고리 | 기존 도서 | 분류 기준 |
| --- | --- | --- |
| 소설 | 데미안, 오만과 편견, 동물 농장 | 성장·인간관계·사회를 다루는 서사 작품 |
| 어린이·청소년 | 어린 왕자, 모모 | 어린 독자도 함께 읽을 수 있는 우화·판타지 작품 |
| 에세이 | 월든 | 자연 속 생활과 삶에 대한 사유를 담은 기록 |

기본 카테고리로 소설, 어린이·청소년, 에세이, 인문, 과학, 역사, 경제·경영, 자기계발, 예술, 시, 기타를 제공합니다. 기존 도서의 내용·평점·좋아요·회원 데이터는 유지합니다.

템플릿 경로는 각 앱의 `templates/<앱 이름>/` 아래에 있습니다. **F417(AI 작가 정보 생성·저장)은 선택 과제로 이번 범위에서 제외했습니다.** 추가 기능인 좋아요 기반 도서 추천에서 GMS API와 `GMS_KEY`를 사용합니다. 별도의 AI 작가 정보 생성·도서 분석이나 리뷰 게시판은 구현하지 않았습니다.

### 동작 규칙

- 비로그인 사용자는 목록·상세를 조회할 수 있습니다. 도서 등록 링크와 수정·삭제 버튼은 로그인 상태에서만 표시합니다.
- 인증이 필요한 화면에 직접 접근하면 로그인 화면으로 이동합니다. 로그인 후 `next`에 담긴 내부 주소로 복귀하며, 외부 주소는 거부합니다.
- 회원 수정과 비밀번호 변경 성공 시에는 명세서대로 도서 목록으로 이동합니다.
- 도서는 공동 책장 데이터입니다. 모든 로그인 사용자가 수정·삭제할 수 있습니다. 회원과 도서 사이의 소유자 관계는 이번 명세서에 없으므로 추가하지 않았습니다.
- 평점은 **0.0~10.0**, 소수 첫째 자리까지 허용합니다. 폼 검증과 DB 제약 조건으로 범위를 확인합니다.
- 추가 독서 정보는 선택 입력입니다. 나이·주간 독서 시간·연간 독서량을 입력할 경우 **1 이상의 정수**만 허용합니다.
- 관심 장르는 `MultipleChoiceField`와 `CheckboxSelectMultiple`로 입력받고 쉼표 문자열로 저장합니다. 변환 로직은 두 회원 폼이 공유하는 메서드에 모았으며, 수정 화면에서는 문자열을 리스트로 되돌려 선택 상태를 복구합니다.
- 회원탈퇴 시 본인의 계정·프로필·세션을 삭제하고, 공동 도서는 유지합니다.
- 없는 도서와 사용자는 404 응답을 반환합니다. 모든 데이터 변경 폼은 CSRF 토큰을 포함합니다.
- 추가 편의 기능으로 제목·저자 검색, 완료 알림, 도서 삭제·회원탈퇴 확인 모달, 모바일 대응 화면을 제공합니다.

## 학습 내용

### 쓰로틀(Throttle): 일정 시간 동안 요청 횟수 제한

쓰로틀은 정해진 시간 간격 안에서 함수가 반복 실행되는 것을 제한한다. 이번 프로젝트의 추천 버튼은 첫 클릭을 즉시 처리하고, 이후 30초 동안 추가 클릭을 무시하는 방식으로 구현했다. 무시된 클릭이 나중에 자동 요청으로 실행되지는 않는다.

- 화면에서는 요청 시작 시 버튼을 비활성화하고, 요청이 끝나면 다시 요청할 수 있을 때까지 남은 시간을 표시한다.
- 외부 API 응답이 느리면 제한 시간이 지나더라도 진행 중인 요청이 끝날 때까지 추가 호출을 막는다.
- 서버에서도 사용자별 캐시 키로 제한 시간과 진행 상태를 확인한다. 새로고침이나 다른 탭으로 화면 제어를 우회해도 현재 서버 프로세스에서는 중복 요청을 제한한다.
- 제한된 요청에는 HTTP 429와 `Retry-After`를 반환하고, 화면은 이 값을 반영해 대기 시간을 안내한다.

외부 API를 호출하는 기능에서는 클릭 제어가 응답 속도뿐 아니라 호출 비용과 사용 한도 관리에도 연결된다는 점을 배웠다. 여러 서버 프로세스로 확장하면 요청 제한 정보도 공유 캐시에 저장해야 한다.

### 디바운스(Debounce): 연속 입력이 끝난 뒤 최종 상태 저장

디바운스는 이벤트가 발생할 때마다 대기 시간을 다시 계산하고, 마지막 이벤트 이후 일정 시간이 지났을 때 실행한다. 좋아요 버튼에는 300ms 디바운스를 적용했다.

- 하트의 선택 상태는 클릭 즉시 화면에 반영하지만, 저장 요청은 마지막 클릭에서 300ms 후 보낸다.
- 짧은 시간에 좋아요와 취소를 반복해 원래 상태로 돌아왔다면 저장 요청을 생략한다.
- 서버에는 단순히 상태를 반전하라는 요청 대신 최종 `liked=true/false` 값을 보낸다. 같은 값을 다시 보내도 결과가 유지되므로 재시도로 상태가 뒤집히는 일을 방지한다.
- 요청 중에 추가 클릭이 발생하면 요청을 순서대로 처리하고 최종 의도를 반영한다. 저장에 실패하면 마지막으로 확인한 상태로 화면을 복구한다.

| 구분 | 디바운스 | 쓰로틀 |
| --- | --- | --- |
| 실행 기준 | 마지막 이벤트 후 일정 시간이 지났을 때 | 정해진 시간 간격에서 허용된 요청만 |
| 적용 기능 | 좋아요 최종 상태 저장 | GPT 도서 추천 요청 |
| 적용 시간 | 300ms | 30초 |
| 목적 | 연속 클릭을 합쳐 불필요한 저장 줄이기 | 반복 호출과 외부 API 사용량 제한 |

두 기능 모두 반복 요청을 줄이지만, 저장해야 할 최종 상태와 즉시 실행해야 할 요청의 성격에 따라 선택해야 한다는 것을 이해했다.

### .env.example: 환경 설정 공유와 비밀값 분리

`.env`는 실제 환경 설정과 비밀값을 보관하고, `.env.example`은 필요한 변수 이름과 예시 값만 공유하는 파일이다. 이번 프로젝트에서는 `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `GMS_KEY`를 예시 파일에 정리했다.

- 실제 `.env`는 `.gitignore`로 제외하고 `.env.example`에는 실제 API 키나 개인 비밀값을 넣지 않는다.
- 새 환경에서는 예시 파일을 참고해 `.env`를 작성하고 발급받은 값을 입력한다.
- `python-dotenv`로 `.env`를 읽되, 이미 등록된 OS 환경변수는 덮어쓰지 않는다.
- `GMS_KEY`는 Django 서버에서 읽고, 브라우저 JavaScript나 템플릿에는 전달하지 않는다.

설정 방법을 공유하는 것과 실제 비밀값을 공유하는 것은 분리해야 한다. 실행에 필요한 변수를 문서로 남기면 다른 환경에서도 설정 누락을 줄일 수 있다.

### 쿼리(Query): 조건 조합과 연관 데이터 조회

Django ORM을 사용해 검색 조건을 SQL 쿼리로 표현했다. 제목 또는 저자 검색은 `Q` 객체의 OR 조건으로 묶고, 카테고리와 개인 좋아요 조건은 `filter()`로 추가해 함께 적용했다.

```python
books = Book.objects.select_related('category')
books = books.filter(liked_users=request.user)
books = books.filter(category_id=category_id)
books = books.filter(
    Q(title__icontains=keyword) | Q(author__icontains=keyword)
)
```

위 예시는 좋아요·카테고리·검색 조건을 모두 선택한 경우의 조회 방식이다. 실제 뷰에서는 사용자가 선택한 조건만 추가한다.

- `select_related('category')`로 도서와 카테고리를 함께 가져와 카드마다 카테고리를 다시 조회하는 N+1 문제를 줄였다.
- 사용자별 좋아요 여부는 `Exists`와 `OuterRef`를 이용해 목록 쿼리에 포함했다. 카드마다 별도의 좋아요 확인 쿼리를 실행하지 않도록 했다.
- 카테고리별 도서 수는 `Count('books')`로 집계하고, 프로필의 관심 카테고리는 `prefetch_related()`로 가져온다.
- URL과 검색 폼에서 조건을 유지해 카테고리를 이동하거나 검색을 초기화할 때도 사용자가 선택한 범위가 일관되게 이어지도록 했다.

조회 결과가 정확한지와 함께 반복 조회가 얼마나 발생하는지도 확인해야 한다는 점을 배웠다.

### N:M 테이블 설계: 사용자별 관계 저장

한 사용자는 여러 도서를 좋아요할 수 있고, 한 도서도 여러 사용자에게 좋아요를 받을 수 있다. 이런 관계는 도서 테이블의 공통 불리언 값 하나로 표현할 수 없으므로, 사용자와 도서를 연결하는 N:M 관계로 설계했다.

| 관계 | Django 모델 필드 | 관계를 저장하는 위치 |
| --- | --- | --- |
| 사용자 N:M 도서 | `Book.liked_users` | `books_book_liked_users` 중간 테이블 |
| 사용자 N:M 관심 카테고리 | `User.interested_categories` | `accounts_user_interested_categories` 중간 테이블 |
| 카테고리 1:N 도서 | `Book.category` | `books_book.category_id` 외래 키 |

- `ManyToManyField`가 생성한 중간 테이블에 연결된 두 객체의 ID를 저장한다. 좋아요 관계가 없으면 해당 사용자에게는 미선택 상태다.
- `book.liked_users.add(request.user)`와 `remove()`로 관계를 관리하고, 역참조인 `request.user.liked_books`로 본인의 도서를 조회한다.
- 같은 사용자·도서 연결의 중복은 중간 테이블의 유일성 제약으로 방지한다. 같은 좋아요 설정을 반복해도 관계가 여러 개 생기지 않는다.
- 관심 카테고리도 여러 항목을 선택하는 관계로 저장해 사용자별로 독립적으로 관리한다.
- 도서에 연결된 카테고리는 `PROTECT`로 보호해 카테고리 삭제 때문에 기존 도서가 함께 사라지지 않도록 했다.

기존 관심 장르는 쉼표 문자열로 저장하지만, 새 관심 카테고리는 실제 카테고리와 연결한다. 데이터의 개수뿐 아니라 중복 방지, 역조회, 삭제 시 동작까지 고려해야 테이블 관계를 제대로 설계할 수 있다는 것을 배웠다.

### Auth 기능: 인증, 접근 권한, 세션 관리

`AbstractUser`를 상속한 커스텀 사용자 모델과 Django Authentication System을 활용했다. `AUTH_USER_MODEL`은 첫 마이그레이션 전에 지정하고, 회원 폼에서도 `get_user_model()`로 같은 모델을 사용했다.

- `UserCreationForm`으로 회원가입 데이터를 검증하고 비밀번호를 해시해 저장한다. 가입 성공 후 `login()`으로 세션을 생성한다.
- `AuthenticationForm`으로 로그인 정보를 검증하고, `request.user`를 기준으로 좋아요·관심 카테고리·추천 대상을 정한다. 클라이언트가 보낸 사용자 ID로 대상을 바꾸지 않는다.
- 일반 화면은 `login_required`로 접근을 제한하고, 좋아요·추천 API는 비로그인 요청에 JSON과 HTTP 401을 반환한다.
- `UserChangeForm`의 수정 필드를 제한해 일반 사용자가 관리자 권한이나 다른 사용자의 정보를 변경하지 못하도록 한다.
- 비밀번호 변경 후 `update_session_auth_hash()`로 세션을 갱신해 변경 직후 로그인 상태가 유지되도록 한다.
- 로그아웃은 세션을 종료하고, 회원탈퇴는 현재 계정을 삭제한 뒤 로그아웃한다.
- 로그인 후 이동할 `next` 주소는 허용된 내부 주소인지 검사한다. 데이터 변경에는 POST 제한과 CSRF 검증을 함께 적용한다.

화면에서 버튼을 숨기는 처리와 서버에서 권한을 검사하는 처리는 각각 필요하다. 인증된 사용자라도 어떤 데이터에 어떤 요청을 할 수 있는지 서버에서 확인해야 한다는 점을 이해했다.

### ModelForm과 데이터 마이그레이션

`ModelForm`으로 입력 검증과 모델 저장을 연결하고, 수정 시에는 `instance`로 기존 데이터를 전달했다. 카테고리는 기존 항목 선택과 새 이름 입력을 함께 지원하되, 다른 필드까지 검증된 뒤에 새 카테고리와 도서를 저장하도록 했다. 공백·대소문자 정규화와 DB 제약 조건을 함께 사용해 중복 생성을 줄였다.

기존 도서에 카테고리를 추가할 때는 테이블 변경과 데이터 채우기를 마이그레이션에 포함했다. 분류 값을 채운 뒤 필수 외래 키로 변경하고, 기존 설명·평점·좋아요·회원 데이터가 보존되는지도 확인했다. 모델 정의를 바꾸는 일과 이미 저장된 데이터를 옮기는 일을 함께 생각해야 한다는 점을 배웠다.

### AI 응답 검증과 실패 상황 테스트

좋아요한 도서를 딕셔너리로 구성해 JSON으로 전달하고, 정해진 JSON Schema에 맞춰 추천을 요청했다. 응답을 받은 뒤에도 필드·자료형·길이·중복을 서버에서 확인한다. JSON 형식이 올바르다는 사실과 도서 정보가 사실이라는 것은 별개이므로, 결과에는 AI 답변의 정확성 안내를 표시했다.

추천 결과는 `textContent`로 출력하고, 상세 링크는 서버가 확인한 내부 도서 주소만 제공한다. 외부 API의 시간 초과·인증 실패·요청 한도·불완전한 응답을 구분해 사용자에게 안내한다. 정상 동작과 함께 연속 클릭, 느린 응답, CSRF 누락, 잘못된 메서드도 테스트해 기능의 경계를 확인했다.

## 느낀점

도서 CRUD에서 시작해 좋아요, 카테고리, 추천 기능을 연결하면서 개별 기능이 동작하는 것과 하나의 서비스로 자연스럽게 이어지는 것은 다른 문제라는 것을 느꼈다. 검색 중 카테고리를 바꾸거나 좋아요를 취소했을 때처럼 작은 상황에서도 목록, 건수, 버튼 상태가 함께 맞아야 사용자가 혼란 없이 사용할 수 있었다.

특히 사용자별 좋아요를 설계한 과정이 기억에 남는다. 좋아요를 단순한 참·거짓 값으로 생각하면 구현이 쉬워 보이지만, 실제로는 누가 어떤 책을 좋아하는지 관계를 저장해야 했다. 사용자·도서·카테고리의 관계를 나누고 중간 테이블과 외래 키를 사용하면서 데이터 모델이 이후 기능과 쿼리의 기준이 된다는 점을 체감했다.

디바운스와 쓰로틀을 적용하면서 버튼 하나에도 여러 상태가 있다는 것을 알게 되었다. 클릭 직후 화면에 보여주는 값, 아직 저장되지 않은 값, 서버에서 확인한 값을 구분해야 했고, 응답이 늦거나 요청에 실패했을 때도 사용자의 마지막 의도가 유지되어야 했다. 단순히 타이머를 추가하는 데서 끝내지 않고 요청 순서와 실패 복구까지 고려한 점이 의미 있었다.

Auth 기능도 로그인 성공 여부만 확인해서는 충분하지 않았다. 회원정보 수정에 허용할 필드, 비밀번호 변경 뒤의 세션 유지, 외부 주소로의 이동 차단, 본인의 좋아요만 조회하는 조건이 모두 연결되어 있었다. 화면의 편의성과 서버의 접근 제어를 함께 설계해야 한다는 점을 배웠다.

환경 설정을 `.env`와 `.env.example`로 나누면서 실행 가능한 코드와 다른 환경에서도 재현할 수 있는 프로젝트의 차이를 생각하게 되었다. 실제 키를 코드에 넣지 않으면서 필요한 설정 이름과 사용법은 공유할 수 있어야 했다. 설정을 문서화하는 작업도 기능 구현만큼 중요한 개발 과정이라고 느꼈다.

GPT 추천은 외부 API 호출 이후의 처리까지 경험할 수 있었던 기능이었다. 응답을 받는 것에 더해 형식을 검증하고 중복을 걸러내며, 요청 비용과 대기 시간을 제어해야 했다. 추천 이유를 함께 보여주면 사용자가 결과를 이해하는 데 도움이 되지만, AI가 생성한 내용을 사실처럼 단정하지 않도록 안내하는 것도 필요했다.

마지막으로 테스트를 통해 정상적인 사용뿐 아니라 실패 상황을 확인한 점이 도움이 되었다. 사용자별 데이터가 섞이지 않는지, 기존 데이터가 마이그레이션 후에도 남는지, 빠른 클릭과 느린 응답에서도 상태가 맞는지를 검증하면서 수정 범위를 더 분명하게 파악할 수 있었다. 기능 수를 늘리는 것과 함께 데이터의 일관성, 조회 효율, 오류 안내까지 챙기는 습관의 중요성을 느꼈다.
